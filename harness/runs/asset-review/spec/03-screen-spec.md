# 화면 설계: 내 자산 등록, 운영자 검수

근거: PRD §6-5, §6-7, §7, §8 Asset, §9, §14, §16 / 서비스 규칙 (story-service.md) / 분석 문서 A1~A13

## 1. 화면 목적

### 1-1. 내 자산 등록
멤버가 만든 프롬프트, 스킬 파일, 자동화 템플릿, 사용 사례를 자산으로 저장하고, 공개 범위를 고르고, 판매 신청 상태를 확인하는 화면이다 (PRD §6-5). 정보 구조상 "내 자산" 섹션에 해당한다 (PRD §5). MVP 1차 필수 항목이다 (PRD §9의 8번 내 자산 등록, 9번 판매 신청 상태).

### 1-2. 운영자 검수
운영자가 멤버가 제출한 판매 신청 자료를 검수 대기 목록에서 열어 보고, 판매 기준 체크리스트로 확인한 뒤 승인 / 수정 요청 / 반려를 정하는 화면이다 (PRD §6-7). MVP 1차에서는 운영자가 수동으로 검수한다 (PRD §6-7 안내문).

## 2. 사용 역할

| 화면 | 역할 | 근거 |
|---|---|---|
| 내 자산 등록 (paid 변형) | paid (유료 회원). 공개 범위는 비공개 / 멤버 공개만 | PRD §7-3 |
| 내 자산 등록 (seller 변형) | seller (판매 승인 회원). 유료 회원 권한 전체 + 판매 신청 | PRD §7-4 |
| 운영자 검수 | admin (운영자) | PRD §7-5 |

guest, free 역할은 자산 등록 화면을 쓰지 않는다 (PRD §7-1, §7-2에 내 자산 등록 권한이 없고, §7-3에서 유료 회원부터 내 자산 등록이 생긴다). admin(운영자)은 내 자산 등록 화면을 쓰지 않는다 (작업자 확정).

## 3. 내 자산 등록: 화면 구성 (위에서 아래로)

역할별로 화면 변형이 2개다. 두 변형은 공개 범위 옵션만 다르고 나머지 구성은 같다.

1. 상단 영역: 뒤로가기와 화면 제목. 분석 A1.
2. 제목·설명 입력 (단일 작성 폼). PRD §6-5 필수 4 "설명 작성", 분석 A1.
3. 파일 첨부. PRD §6-5 필수 3.
4. 분류·태그 선택. 고르는 항목은 칩·태그로, 선택지가 긴 항목은 바텀시트 목록으로 나눠 폼이 길어지지 않게 한다. 분석 A3. (Asset 모델의 category, tags 필드에 대응, PRD §8)
5. 공개 범위 선택: 라디오 버튼 그룹, 옵션마다 한 줄 설명. 아래 §4 참고. PRD §6-5 필수 5, 분석 A2.
6. 하단 고정 버튼 영역: 임시저장(보조)과 저장/등록(주)을 나란히 둔다. 임시저장은 상태 "임시저장"과 연결된다. 분석 A1.
7. 내 자산 목록과 상태 배지. 아래 §6 참고. PRD §6-5 필수 1·6, 분석 A5.

폼이 길어질 때 진행 표시(2/3 같은 단계 표시)로 나눌 수 있다. 제안 (분석 A4): PRD에 등록 단계 구분은 없다. 채택 여부는 G2 확인 때 정한다.

## 4. 공개 범위 (역할별 변형)

- 기본 선택값은 항상 "비공개"(private)다. 멤버가 만든 자료는 기본이 비공개이고, 본인이 선택할 때만 멤버 공개나 판매 신청이 된다 (PRD §14, 서비스 규칙 1).
- paid 변형: 옵션은 비공개(private) / 멤버 공개(member_only) 2개다 (PRD §7-3).
- seller 변형: 옵션은 비공개(private) / 멤버 공개(member_only) / 판매 신청(sale_request) 3개다 (PRD §7-4).
- 판매 신청은 판매 승인 회원(seller)만 선택할 수 있다. paid 변형에는 판매 신청 옵션을 두지 않는다 (PRD §6-5 필수 5, §7-4).
- 각 옵션 옆에 한 줄 설명을 붙인다. 분석 A2. (설명 문구 자체는 PRD에 없어 시안 단계에서 정한다.)
- 데이터 모델의 `visibility` 필드가 이 값에 대응한다 (PRD §8 Asset). 화면 옵션 "판매 신청"은 모델 값 `sale_requested`와 연결된다.
- 유료 회원(paid)이 판매 신청을 하려면 운영자가 역할을 seller로 바꿔야 한다. 승인 요청은 앱 밖에서 받는다 (PRD §7-4). 이 화면에서 승인 요청을 받는 구성은 없다.

## 5. 상태별 화면 동작 (내 자산 등록)

상태 이름은 PRD §8 Asset의 `review_status`를 쓰며, 화면 표기는 PRD §6-5를 따른다.

| review_status | 화면 표기 | 화면 동작 |
|---|---|---|
| draft | 임시저장 | 작성 중인 자산. 폼에서 자유롭게 수정할 수 있고, "검수 요청" 버튼으로 제출한다 (작업자 확정) |
| pending | 검수 대기 | 운영자 검수를 기다리는 상태. 목록 배지로 상태를 확인한다. 검수 대기 중에는 수정할 수 없다 (작업자 확정) |
| revision_requested | 수정 요청 | 운영자가 수정을 요청한 상태. 운영자가 남긴 수정 요청 코멘트를 함께 보여준다 (PRD §6-7 필수 5). 수정 요청을 받으면 고친 뒤 다시 제출할 수 있다 (작업자 확정) |
| approved | 승인됨 | MVP 1차의 최종 상태다 (PRD §6-5, §9 결정 사항 5). 목록 배지로 표시한다 |
| rejected | 반려 | 운영자가 반려한 상태. 목록 배지로 표시한다. 반려는 재제출 없이 종료다 (작업자 확정) |

- 임시저장(draft)에서 검수 대기(pending)로는 "검수 요청" 버튼으로 간다 (작업자 확정). 이 동작의 이름은 PRD에 없다.
- 승인됨 이후 상태(PRD §8의 suspended 등)와 Phase 2 상태는 이번 설계에 넣지 않는다.
- 상태가 바뀌면 알림이 간다 (PRD §6-8 필수 4 "판매 신청 상태 변경", 5 "자산 승인/반려"). 알림 화면은 이번 묶음 화면 목록에 없다.

## 6. 내 자산 목록과 상태 배지

- 목록의 각 항목 오른쪽에 상태 배지를 붙이고, 상태별로 배지 색과 글자를 구분한다. 배지 종류는 임시저장 / 검수 대기 / 수정 요청 / 승인됨 / 반려 5가지다. 분석 A5.
- 상태별 탭 또는 칩 필터를 목록 상단에 둘 수 있다. 제안 (분석 A6): PRD에 필터 요구는 없다. 채택 여부는 G2 확인 때 정한다.
- 판매 신청 상태 확인은 판매 승인 회원(seller)의 권한이다 (PRD §7-4). paid 변형은 판매 신청이 없으므로 판매 신청 상태 배지를 보지 않는다 (작업자 확정).

## 7. 운영자 검수: 화면 구성 (위에서 아래로)

1. 검수 대기 목록. 카드형 항목 + 상태 배지 구조에 제작자, 제출일, 자산명을 한눈에 보이게 한다. PRD §6-7 필수 1, 분석 A7. 오래된 순으로 정렬하고 상태 필터는 두지 않는다 (작업자 확정).
2. 자산 상세 보기. 제출된 설명·첨부 파일·사용 방법을 내 자산 상세와 같은 정보 순서로 보여준다. PRD §6-7 필수 2, 분석 A13. (PRD §16이 자산 상세를 "내 자산 상세, 운영자 검수 상세용"으로 정한다.)
3. 판매 기준 체크리스트. 상세 아래 또는 하단 영역에 이어 붙인다. 아래 §8 참고. PRD §6-7 필수 3, 분석 A8·A13.
4. 가격 설정 또는 가격 승인. 아래 §9 참고. PRD §6-7 필수 7, 분석 A12.
5. 하단 고정 결정 버튼 영역: 승인(주) 1개, 수정 요청·반려(보조) 2개를 구분해 배치한다. PRD §6-7 필수 4, 분석 A11.

## 8. 판매 기준 체크리스트 (PRD §6-7 "판매 가능한 자료 기준")

체크리스트는 검수 때 필수로 사용한다 (PRD §6-7 필수 3). 체크박스 목록으로 세로로 나열하고, 상단에 "전체 확인" 행을 둔다 (분석 A8).

1. 실제 업무에 써본 것
2. 결과 예시가 있는 것
3. 사용 방법이 명확한 것
4. 초보자가 따라할 수 있는 것
5. 특정 툴/버전/환경 조건이 적혀 있는 것
6. 개인정보/고객정보/회사기밀이 없는 것
7. 저작권 문제가 없는 것
8. 구매자가 바로 써볼 수 있는 것

- 6번(개인정보/고객정보/회사기밀)과 7번(저작권) 항목은 필수 표시로 눈에 띄게 한다 (분석 A8, PRD §14 근거).
- 항목마다 판단 기준 문구는 붙이지 않고 PRD 원문 8개 문구만 보여준다 (작업자 확정). 분석 A10(항목별 펼침 영역)은 이번에 반영하지 않는다.
- 체크리스트를 다 채우기 전에는 승인 버튼이 비활성이다. 8개를 모두 체크하면 활성으로 바뀐다 (분석 A9, 서비스 규칙 2, 작업자 확정). JSON의 `approve_enabled_before_checklist_complete`는 `false`다.
- 수정 요청·반려 버튼은 체크리스트와 무관하게 언제든 쓸 수 있다 (작업자 확정).

## 9. 가격 설정/승인과 수정 요청 코멘트

- 가격 설정 또는 가격 승인: 운영자 검수의 필수 기능이다 (PRD §6-7 필수 7). 데이터 모델의 `price` 필드에 대응한다 (PRD §8). 판매 신청자(seller)가 등록 폼에 희망 가격을 입력하고, 운영자가 검수 화면에서 그 가격을 승인하거나 고친다 (작업자 확정). 따라서 seller 변형 등록 폼에는 희망 가격 입력란이 있고 paid 변형에는 없다. 통화·형식은 PRD에 없어 시안 단계에서 정한다.
- 수정 요청 코멘트: 수정 요청·반려를 고르면 코멘트를 입력한다 (PRD §6-7 필수 5). 판매 검수 절차이며 미션의 코멘트 기능과는 별개다.
- 제안 (분석 A12): 코멘트 입력과 가격 설정·승인 입력을 바텀시트로 연다. PRD에 표시 방식은 없다. 채택 여부는 G2 확인 때 정한다.

## 10. 상태 전환 (운영자 검수)

검수 대기(pending)에서 나가는 전환만 이 화면에 있다.

| from | to | via_review | 설명 |
|---|---|---|---|
| pending | approved | true | 체크리스트 8개를 모두 채운 뒤 승인 버튼으로만 간다 |
| pending | revision_requested | true | 수정 요청 코멘트와 함께 |
| pending | rejected | true | 반려 |

- 승인됨(approved)으로 가는 전환은 검수를 거치는 위 한 가지뿐이다 (PRD §14, 서비스 규칙 2).
- 임시저장에서 검수 대기로 가는 전환은 내 자산 등록 화면(제출)의 몫이며 이 문서의 JSON에는 넣지 않는다.

## 12. 작업자 확정 사항 (PRD에 답이 없던 것)

1. 가격: 판매 신청자(seller)가 등록 폼에 희망 가격을 입력하고, 운영자가 검수 화면에서 승인하거나 고친다.
2. 수정 요청을 받으면 고친 뒤 다시 제출할 수 있다. 반려는 재제출 없이 종료다.
3. 검수 대기 목록은 오래된 순으로 정렬하고 상태 필터는 두지 않는다.
4. 승인 버튼은 체크리스트 8개를 모두 체크해야 켜진다. 수정 요청·반려는 체크리스트와 무관하게 언제든 쓸 수 있다.
5. 체크리스트 항목마다 판단 기준 문구는 붙이지 않는다. PRD 원문 8개 문구만 보여준다.
6. 임시저장 상태에서는 자유롭게 수정하고 "검수 요청" 버튼으로 제출한다. 검수 대기 중에는 수정할 수 없다.
7. 유료 회원(paid)은 판매 신청 상태 배지를 보지 않는다. 운영자는 내 자산 등록 화면을 쓰지 않는다.

## 13. 확정 사항 요약

- 내 자산 등록은 paid, seller 두 변형이다. 공개 범위 기본값은 두 변형 모두 private이고, 판매 신청(sale_request) 옵션은 seller 변형에만 있다.
- 운영자 검수 화면은 admin 전용이며, 체크리스트 8개는 PRD 원문 그대로이고 승인 버튼은 체크리스트 완료 전에 비활성이다.
- 승인됨으로 가는 전환은 검수를 거치는 것뿐이다.

```json
{
  "screens": [
    {
      "screen": "내 자산 등록",
      "variant": "paid",
      "kind": "asset_form",
      "roles": ["paid"],
      "visibility": {
        "options": ["private", "member_only"],
        "default": "private"
      }
    },
    {
      "screen": "내 자산 등록",
      "variant": "seller",
      "kind": "asset_form",
      "roles": ["seller"],
      "visibility": {
        "options": ["private", "member_only", "sale_request"],
        "default": "private"
      }
    },
    {
      "screen": "운영자 검수",
      "kind": "admin_review",
      "roles": ["admin"],
      "review_checklist": [
        "실제 업무에 써본 것",
```
